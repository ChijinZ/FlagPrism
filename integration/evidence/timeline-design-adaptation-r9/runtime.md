# R9 独立设计评审：运行时、留存与离线派生

评审范围：`Profiler/docs/timeline_design.md`（重点 §0、§8.13–8.14）及 `timeline_testing.md`（重点 §8.8–8.9）；抽查 `timeline_runtime.py`、`hooks/timeline.py`、`timeline_perfetto.py`、`timeline_unit_nvidia.py`。未查看本轮其他报告，未连接服务器、执行产品测试或修改实现。本报告不是最终代码验收。

## 结论

**设计方向合理，工程上可实施；可以据此推进小纵向实现，但尚不宜称实施合同已经完全闭合。** 五部件的分工能将设备完成/发布协议留给 transport，将公共 owner、身份和导出留在公共链；这比复制整个 profiler 或强迫统一物理 ABI 更实际。单位、边界、误差、epoch 和动态关联分别授予资格，也允许有价值的局部信息先交付而不伪造流水。

本轮新增的不可变原件、内容寻址派生、独立 provider 重核、新进程重导和并发失败验收，直接覆盖了当前实现的实际缺口。未发现必须推翻架构的 P0。下列 P1 应在实现对应功能前明确；主要是提交/发现/恢复的精确定义，不需要新建庞大的插件体系。

设计合理不代表三个后端已具备源区域边界、可比较时钟或完整异步资格。现有 counter-ns 能打开，不能据此填 P01/全量资格通过。

## P0

无已发现的架构性 P0。若实现仍用当前固定 observer 文件名和无跨进程协调的替换写入宣称完成补证/并发重导，将违反新合同；这是明确待修实现，不是设计已通过的能力。

## P1：实现前补足的决策

### P1-1：将派生事务的提交点和恢复发现规则写死

位置：设计 §8.14“原件和派生物分别版本化”；测试 §8.9“派生失败恢复”。

设计已经要求原子索引和不发布半成品，但尚未明确：trace 已落盘、收据未提交、索引未更新时，新的进程怎样区分可重用完成产物和未完成残留。仅原子更新 HTML 或 JSON 不能使多个派生文件一起提交，也不能防止索引读到缺文件或遗漏合法并发结果。

建议采用最小事务：内容寻址派生目录 → 写全部输入/视图/trace → 核摘要并 fsync → 最后原子发布不可变完成收据；索引只枚举有效收据。索引更新使用同一 bundle 内有界串行锁，锁内重读并合并，或从收据集合重新生成。未完成文件不进入索引，下次可以确定性补齐/重核。明确锁等待超时、进程退出自动释放和不删除他人锁的规则；不必实现分布式锁。

测试在已有“trace 后索引前失败”之外，增加**拥有锁的子进程被终止**与收据/索引发布边界故障。用服务器 Docker 的临时目录和自己拥有的进程即可，不碰设备任务。校验新进程能恢复、旧 SHA 不变、两个合法派生均可发现。当前 `_persist` 的 exists/read/replace 不是跨进程 compare-and-create；实现不能据此声称已经防竞争。

### P1-2：明确 canonical 升级也是派生，不把旧 canonical 固定成唯一真相

位置：设计 §8.12 的回绕兼容、§8.14 派生身份；测试 §8.9“补证与升级”。

合同同时允许未来 decoder/schema 从同 raw 重读，并要求 canonical SHA 与首次结果不变。两者可以共存，但必须明确“旧 canonical 文件不改”不等于“新 reader 只能消费旧 canonical”。新 decoder 可能恢复旧 reader 无法配对/展开的事件，必然得到不同 canonical 内容。

建议区分：不可变原始捕获（raw、布局/发布/编译/调用快照）→ 带 decoder/schema 身份的不可变 canonical revision → 带 proof/mapper/exporter 身份的 view revision。原始 capture ID 不变，各 revision 有自己的完整输入摘要。测试同 raw 用旧 reader 保存原结果，再用合法新版产生新 canonical 与视图；旧文件均不变、两条派生链可追溯，无应用重放。用 fixture 验证版本合同即可，不要求当前硬件实际跨回绕。

### P1-3：规定跨进程重导所需的最小离线输入闭包

位置：设计 §8.13 原件持久化/释放、§8.14 跨进程恢复；测试 §8.9“幂等重导”。

“所需证据”原则正确，但实施者仍可能只保存 proof JSON、绝对路径或原进程内对象。实际重导还可能依赖 binary、PTX/反汇编、source manifest、布局/发布协议、调用选择和 host window。缺一个就无法独立重核。scratch 的释放条件应以这份闭包已持久化为准，而不是仅 raw 文件写完。

建议每个 capture 提供版本化 original-input manifest，列必需文件及摘要、相对路径、解码/provider 规则身份、捕获时取得的 epoch/window 证据；完成收据只在它们全部留存后发布。公开重导入口接受 bundle 路径和显式规则/proof 输入，不依赖原 hook/session。验证时关闭原进程、让原缓存/工作目录不可访问，在新进程仅持有 bundle 及已安装工具运行；缺证失败应定位具体文件/事实且保原件。

当前原件先保留再释放 owner 的顺序可复用。离线重导是新的公开调用者，不应重新创建 device owner 或要求可用 GPU。运行在服务器 Docker 仍符合执行边界。

### P1-4：补一个“磁盘留存失败时 owner”的明确恢复用例

位置：设计 §8.13 的 raw_ready_not_persisted、§8.14；测试 §8.8/§8.9。

设计已表达持久化失败时保 host bytes、完成不等于持久化，但多数故障用例集中在 readback/decode/export。raw 写成功、关联文件写失败或 fsync/rename 失败，正好处于可释放设备与可离线恢复之间，最易出现孤儿文件、重复累计预算或丢失原件。

建议明确：失败不发布完整捕获收据；保已有 host bytes/身份与必要资源；重试允许重用相同内容的已落盘文件，补齐其余闭包，不重读应用或重复累计原件。全部捕获输入安全持久化才释放，完成未知的其它 owner 不受影响。用受控文件写入/fync 错误注入，不真正耗尽服务器磁盘；记录首次失败和第二次结果。还要覆盖 release 本身失败后的重试，不重复释放已释放子资源。

## P2：可改善但不阻塞最小纵向链

1. **设计 §0 与 §8.14 的阅读成本**：新增执行入口有效，但 §8.1–8.14 有多轮相近合同。后续可将每个已生效决策指向唯一当前章节，旧节明确为历史依据，避免实现者从旧“raw+clock 一起解码”推导 clock 是物理解码必需参数。不建议本轮再加一套状态表。
2. **测试 §8.9 的确定性边界**：定义摘要规范（JSON 键顺序、字符串编码、schema 版本；排除运行时间/绝对路径等非语义字段）和 ID 冲突检查。语义相同但字段顺序不同不应产生随机 revision；不同 proof 内容必须不同 revision。可用 CPU 合同测试，不额外加设备矩阵。
3. **设计 §8.14 的证据更新语义**：明确旧视图是“按当时输入生成的历史结果”，不能因补证自动改写为最新；若新证据撤销旧资格，索引应显示撤销/替代关系，不把历史 trace 静默当当前推荐结果。proof 的内容寻址能留历史，但本身不表达撤销。

## 尚未实证的关键可行性风险

- NVIDIA 的源区域边界与普通/插桩调度保持：counter 机器 PC 和正 duration 不足以证明。这是方法正确性的主要风险，须优先核最终对象。
- GCU 真实计时单位、所需精度和异步机制覆盖；Ascend 新 timeline 发布/可见性和 AIC/AIV 必需时间比较；不能由公共 owner 合理推导成功。
- 每后端真实两代 buffer/flag 复用、partial wait/缺失事件的恢复锚点。必须来自实际 lowering/SDK，不能靠 mapper 自我验证。
- 共享 deadline 只对可中断/可界定的 SDK 操作有意义；无法取消的 readback 仍需持有 staging/context 与完成依赖，不能把 Python timeout 当实际停止。
- 标准 Perfetto 的导入、可见性、语义可理解分别验收；SQL 正确不替代 UI，UI 漂亮也不授予 precision 或 engine busy。

上述风险不是要求扩大资格矩阵，而是决定应先运行哪条最小链。未证明之前保留 partial 是正确行为，但仍未满足完整目标。

## 最小验证顺序

1. **固定一份真实留存 bundle，先验证纯离线链。** 新进程重新核输入闭包、raw 引用与当前单位 provider；无设备调用。一次合法重导、同输入重导、伪 view/同路径变证据负例。全部在服务器 Docker。
2. **完成派生版本/事务合同。** 两份合法 proof 或规则版本得到两个不可变 revision；并发重导、故障前后重启、锁进程终止恢复、索引无半成品。以同一 bundle 重用，不增加算子次数。
3. **验证 owner 留存边界。** 使用已有真实多调用数据链，结合受控 write/readback/release 故障；检查 raw-first、就绪者优先、共同 deadline、未持久化状态和预算计数。生命周期 fixture 与真实设备正例分别标记。
4. **每后端最小循环与真实异步样本。** 先最终对象合法边界与调度对照，再发布/回收、本地时间、两代复用、所需时钟比较；发现硬限制就保完整最小证据，不先扩量。
5. **再进入独立数学、完整 SQL/UI 和额外代码审阅。** 本轮文档评审不替代这些门，不按三个设计 reviewer 投票决定设备可用。
