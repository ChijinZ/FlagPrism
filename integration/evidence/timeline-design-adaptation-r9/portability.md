# 独立设计评审：适配边界、时间资格与可实施性

评审范围：`Profiler/docs/timeline_design.md`，重点 §0、§8.12–8.14；`timeline_testing.md`，重点 §8.9。为核对设计与现状，静态查看 `timeline_runtime.py`、`timeline_views.py`、`timeline_unit_nvidia.py`、`timeline_perfetto.py`、`hooks/timeline.py`。代码基线 `691846f58ebd7b7ebda1f02c6a73fd1d5ba55370`；设计为工作区本轮修订。没有读取本轮其他 reviewer 报告，没有运行产品、连接设备或修改设计/产品代码。

## 独立结论

**设计合理，可作为下一步实现合同；实际三后端可行性仍是有条件成立，不能由本评审授予。** 没有发现必须推翻公共抽象的 P0/P1 设计矛盾。五个适配部件按变化原因拆分，比“每芯片一个完整 backend”或强制统一设备 ABI 更合理；单位、源边界、精度、epoch、机制完整性分别授资格，能够保留异构细节，同时复用公共消费者。

新增芯片的成本可被隔离，但不能据此断言成本小。相同工具链/ABI/runtime 的新型号主要补目标资格；不同编译链或发布/异步机制仍可能需要显著工程。文档明确不承诺固定工期、不用类数/LOC/假后端证明适配成功，这一界线正确。

标准 Perfetto 路径在数据模型层面可实施：本地 counter-ns 与真正 source-region elapsed 分开；不能比较的域分文件；有真实动态关联、端点语义和可比时钟后才允许时间 flow。它没有要求 Perfetto 自动创造设备同步关系。完整三后端异步目标能否达到，取决于实际 SDK/对象提供的 timer、合法边界和 generation 来源，目前不能从文档确定。

## P1：实施放行前必须闭合，不能当成设计已经完成

### P1-I1：现有公共 owner 输入仍带 NVIDIA 形状；设计已禁止继承，但尚未形成完整中性实现

定位：设计 §8.13“公共复用的是预算、调用身份与潜在写者状态机”；`timeline_runtime.py:91` 的 `prepare(... function, num_ctas, device, stream)`，其中 `stream` 仍强制非负整数（约第107行）；只有 executable 已有 transport 校验扩展。设计 §8.14 transport 行明确“不要求 NVIDIA 句柄形状”。

影响：如果直接要求 Ascend 等新 transport 填整数 stream/CTA 等字段，五部件拆分会在真实接入时重新变成 CUDA 形状的适配层。该风险是现有代码债，不是新增合同错误。

最小动作：第二个真实调用者接入时，以后端校验的 executable/context/queue 与物理布局需求承接这些输入；没有语义的字段不造占位值。保 NV 旧调用兼容或显式版本迁移。验收用已有三后端公开入口追踪；CPU fixture 仅补“不兼容句柄被拒绝/合法后端对象通过”的合同覆盖，不能冒充设备接入。

### P1-I2：现有派生文件身份不足，尚不满足补证/重导合同

定位：设计 §8.14“原件和派生物分别版本化”（第452行）；测试 §8.9“补证与升级”“派生失败恢复”；`timeline_perfetto.py:183` 的 `write_counter_exports` 当前以 invocation 前缀和 observer ID 命名，无完整 proof/规则/exporter 摘要分区。

影响：合法新 proof 或 exporter 版本在同一原件上生成不同字节时可能撞上不可变文件；只修改 index 或覆盖旧文件也不符合合同。跨进程重导和同时补证时尤其明显。设计本轮新增规则直接解决了这一问题，不能把当前局部 ns 成功填成这一门通过。

最小动作：先冻结一个很小的确定性 derived-input 清单编码：raw/canonical、manifest、invocation、proof 实际内容/证据摘要及有关规则版本；按其摘要发布不可变产物，再原子提交收据/索引。进程中断后只能发现完整提交或可恢复的未提交产物。沿测试 §8.9 用真实 bundle 在新进程重导两次，再改变合法 exporter 版本，最后做并发不同 proof 与索引前故障；核旧 SHA 保持、无应用调用、成功索引不含半成品。

## P2：建议在实施落点明确的小事项

### P2-D1：将“必需版本”落实为部件间有限兼容条件，不建立全排列兼容平台

定位：设计 §8.14 第448行、测试 §8.9 第280行。

合同本身正确，但“任一必需条件未知拒绝”需要实现明确哪些条件实际被消费。例如 clock 缺资格应使 ns/时间箭头不可用，并不使已合法采集的 raw 无效；mapper 更改不应强制未使用该机制的调用重编译。建议每条兼容检查附上依赖方向、检查阶段、缺失影响和一个实际调用者。沿真实三后端列必要边，不测试无意义的所有版本组合。当前“沿实际依赖失效”足以允许这种有限实现，无需增加一套大型框架。

### P2-D2：重导锁的失败终态要成为可定位诊断

定位：测试 §8.9 第285行允许显式串行锁。

这一实现选择实际可行。落地时需写明有界等待/冲突诊断及进程异常后的释放策略；不把无限等待或删除不可验证的其他进程锁当恢复。建议采用进程退出自动释放的 OS 级锁，产物仍按不可变发布与原子收据决定完整性。此项不需要改动事件模型。

## 不能从设计推断已经解决的风险与最小验证路径

| 未实证风险 | 最小实际路径 | 必须保留的失败结论 |
| --- | --- | --- |
| 自动区域边界是否包住声明的执行且没有改变目标流水 | 每后端一份 runtime-K 依赖循环，加一份 ordinary 对象确有异步的样本；对 ordinary/疏/密观测分别核最终对象、数据依赖、已有 submit/commit/wait/compute 顺序和数学结果 | counter PC/正 duration 不授边界；改变调度不能解释为原程序无扰动流水 |
| GCU/Ascend 时间单位、读取误差及必要跨主体关系 | 核实际 getter、位宽、比例与适用目标；独立窗口排除整圈；独立校验有覆盖范围；对应实际两主体/语义泳道分析共同 epoch 或有界关联 | 单位成立仍可只有 counter bracket；有限统计结果不是所有运行的硬上界；比较不足不画 flow |
| 两代物理复用与 wait 覆盖是否可观察 | 真实机制、真实控制路径下至少两代 slot/flag，证明本次 operation/group、wait 覆盖及代际来源；缺失/错代以合同负例核拒绝 | 逻辑 ordinal 不冒充物理 generation；只知道依赖并不说明硬件 busy/重叠 |
| 不同物理发布协议能否共享消费者 | 三后端保各自 ABI；从真实 bytes、精确字段 offset 和发布规则进入公共事件，再走相同 clock/identity/Perfetto 检查 | 某后端未发布/坏 guard 保原件，不能由 decoder 猜补；fixture 不授设备资格 |
| 完整 UI 是否真的可读 | 先对最小实际 trace 进行真实 TP SQL，后按原门打开标准 UI、选择区间/详情与真实 flow；已知域隔离和未知精度直接可见 | SQL 正确不替代 UI；counter-only 单条可打开不完成完整异步门 |

推荐执行顺序与文档一致：第一条实际纵向链尽早接公共 exporter/SQL，冻结被实际消费的小合同，再复用到第二、第三后端；先解决上述最小样本的硬缺口，再扩完整数学矩阵。不可观测的 SDK 事实不能靠更多测试或改写状态表补齐，应按 §8.14 报最小技术阻碍并继续不依赖该阻碍的工作。

## 验收设计判断

§8.9 将真实设备正例、同原件负例、新进程重导、版本化补证、并发/中断发布分别列出，均可转化为确定动作和断言。没有强迫制造不存在的替代硬件，也未要求所有后端使用相同物理布局/warp/SM 或同一异步规则。这一验收边界实际可执行。

本报告仅通过设计方向及验收可操作性；上述 P1 实施缺口和设备风险须按实际证据闭合，不替代独立数学资格、三后端完成状态或交付后的三名额外代码审阅。

## 有限复核：本轮修订后的处置

仅复读修订后的设计 §8.14 与测试 §8.9，未扩大代码审计、未运行设备，不读取其他 reviewer 报告。

- **P2-D1 已在设计层解决。** “确定性与历史”明确兼容检查只覆盖三后端实际使用的依赖边，并标明检查阶段/失效范围，不建立全排列平台。这与单位、边界、epoch 分别授资格一致，不会因 clock 缺证而无条件推翻 raw。
- **P2-D2 已在设计层解决。** “派生提交与恢复”明确 bundle 内 OS 级有界锁、退出释锁、冲突诊断、锁内合并/枚举收据和原子索引；测试新增终止自己持锁子进程的恢复案例。它可用有限的进程级实现完成，不要求分布式事务服务。
- **新增条款未发现新的设计矛盾。** 输入闭包使离线重导不再隐含依赖原缓存/对象；canonical revision 允许 decoder 升级且保旧结果；规则绑定实际安装内容指纹，避免只改实现不改版本导致身份误复用；撤销/替代追加记录避免把历史资格继续推荐为当前有效。边界收据限定公共层核引用、后端核支持模式，不要求任意机器码通用证明器，实际可实施。
- 这些合同增加的是持久化/离线消费的工程量，不增加第四硬件或独立数学数量。实现仍应先打通真实最小数据链，再用同一真实 bundle 执行故障与升级测试；不能在尚缺 timer/合法边界/真实机制时优先把索引体系做成独立平台。

**复核结论保持：设计可接受，原两项 P1-I1/P1-I2 实施债仍未关闭。** 本轮修改没有设备通过或最终代码验收含义；收据、锁、指纹等实现也仍须按新增测试给实际结果。
