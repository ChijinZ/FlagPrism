# 独立设计评审：compiler / 最终对象 / 发布协议

审阅对象：`Profiler/docs/timeline_design.md`（重点 §0、§4–8、§8.12–8.14）与 `timeline_testing.md`（重点 P01/P03/P05/P07/P10、§8.7–8.9）。审阅同时抽查 `AutomaticScopes.cpp`、`timeline_nvidia_async.py`、`timeline_views.py`、`timeline_unit_nvidia.py` 与 `timeline_perfetto.py` 的职责落点。仅审设计及可实施路径；未运行产品、未连接服务器、未读取本轮其他报告，不是最终代码验收。

## 独立结论

**设计职责分配合理，可以按最小纵向链实施；三后端完整交付的实际可行性仍有三项关键待证，不能从设计通过推导设备通过。** 本轮新增 §8.14 没有引入必须先完成的大型插件平台，版本及派生合同能够用现有函数、确定性内容摘要、磁盘原子提交和有界锁完成。编译、transport、decoder、clock 与 mechanism 拆分有实际变化原因；统一物理 ABI、统一 warp/SM 或统一时钟资格均不是前提。这适合后续新增芯片。

未发现必须推翻五部件设计的 P0，也未发现新增 §8.14 / 测试 §8.9 之间的 P1 硬矛盾。下列 P2 是建议明确的判定细节；另列的三项 P1 级实施风险是本轮设备放行前必须取得实证的工作，不能以文字修订代替。

## 设计问题与可实施修订

### P2-1：明确 `end≥start` 针对哪一种值，避免回绕验收冲突

- 依据：测试 §4 写“单位和 epoch 证明有效，end≥start；回绕只在唯一可解的位宽/窗口内处理”；设计 §8.12 又明确未来 modulo 版本保留 start/end 原始值，可以合法出现原 tick 下降；测试 §8.7 已给 `start=2^b−2, end=2` 正例。
- 问题：如果自动验收将 §4 的 `end≥start` 直接施加于保留的原始 tick，会错误拒绝未来合法回绕派生，或者诱使实现篡改 raw。
- 建议：改成“原始 modulo tick 保持不变；只有经有效窗口唯一展开后的坐标和导出 ns 要求 end≥start。当前不支持回绕的 schema 明确拒绝时间解释并保原件”。不要求本轮无实际需求时提前写新 schema。

### P2-2：将边界证明具体落实为每种支持结构的证据记录，避免只有人工一句‘已核对象’

- 依据：设计 §4、§8.6、§8.11、§8.12；测试 P03、§8.6 P03、§8.9 最小纵向证据已要求最终对象和源边界。
- 问题：方向正确，但尚未在设计中举出一份足以复核的边界收据最小结构。仅保完整反汇编和一个状态位，会让后续型号适配者不清楚需要从哪里复核支配、循环位置和纯算术依赖；反过来，要求通用 validator 自动证明任意机器码语义也不现实。
- 建议：在现有 manifest/证据中至少定位 `binary/function/section`、begin/end 读钟及 marker 的机器位置、被声明区域的指令范围或基本块集合、控制路径/循环、依赖约束的产生层与实际结果、未覆盖情况。公共 validator 只核绑定、范围、引用和资格；后端证据检查器核真实指令模式；陌生优化形态返回未证，不能凭 PC 邻近授予边界。允许针对有限通用结构逐步实现，不新增逐算子适配表。
- 性质：这是让既有要求可审计的细化，不是要求另造完整反编译器或为每条 slice 做形式化机器证明。

### P2-3：明确派生身份中的构建规则摘要，而不只写人为版本字符串

- 依据：设计 §8.14 “实际 proof 内容及证据文件摘要、decoder/mapper/转换规则与 exporter 版本”；测试 §8.9 已测规则升级及同路径证据内容变化。
- 问题：proof 和证据内容摘要已明确，但如果 exporter/mapper 实现变化且人工版本字符串漏升，仍可能得到同一派生路径并触发不可变冲突。当前 `write_counter_exports` 以 observer 路径写入，也正需要按新合同整改；当前缺口不代表合同已经实现。
- 建议：规定这些“版本”至少绑定已安装实现的稳定内容/构建指纹，或规定构建期强制生成的不可漏升规则 ID；明确发布版本号只作展示，不独自承担派生缓存身份。验收加入“公开版本文字相同、实现指纹变化”的合同负例，沿用既有 P08/P10，不扩设备数学。

## 尚须实证的关键风险（P1 级放行风险，非已证明不可能）

### R1：自动源区域边界与 ordinary 流水保真

当前早期 `AutomaticScopes.cpp` 插入 Record 的调用点以及机器 counter 映射，不单独保证最终纯算术没有穿越边界，也不保证异步流水保留。设计已正确点明普通/插桩 GEMM 的展开及调度变化。noinline、SSA 依赖、volatile 或 memory clobber 都只能是候选手段。须在运行时依赖循环、归约和真实异步机制各核实际对象；若保护边界使 async schedule 人为串行化，必须调整通用插桩层级/采样策略，不能把新图当 ordinary 执行解释。

这是本轮最强风险，既涉及编译器实现也涉及可解释语义。最小样本失败时停止扩大矩阵是合理且必要的。

### R2：真实物理复用和动态依赖记录，而非只数逻辑 commit group

`timeline_nvidia_async.py` 明确只产生 cp.async 的逻辑 group 事实，不提供物理 buffer generation 或时间箭头。这与设计诚实一致，也说明 P07 尚有实际实现工作。若普通 lowering 已复用 shared-memory 位置，需在该 lowering 能看到实际地址/slot、循环及 wait 覆盖时形成静态规则，并在真实路径记录必要动态状态。SSA 的源码 buffer 名称或按日志 occurrence 编号不能替代。

异构后端必须各自核 set/wait、group/flag 与实际生产消费语义；公共 validator 负责引用/代际，不会自动知道 ISA 是否真实保证完成。五部件边界容得下这项工作，但并未消除工作本身。

### R3：Ascend 发布/回收协议及 GCU 单位证明

不同 actor 的真实可见性、cache-line/padding、logger/publisher 版本与完成条件必须从当前目标/SDK 对象与真实 bytes 闭合，不能继承 census 或旧 advanced 资格。GCU 的 timer 名称和旧近似校准不自动授予当前实际 getter 的尺度/误差/epoch。当前 NV `counter_unit_only` 也是局部坐标，不能填充这些后端的资格。

设计允许独立布局、原件先落盘、未知时钟隔离，故没有发现结构性不可落地；但 SDK 是否开放足够插桩点和时钟信息，只有最小设备链能回答。若确认硬限制，须报告用户，不能在设计层声称必然能解决。

## 最小验证路径

1. 每后端锁定普通 `load → runtime-K 依赖循环 → store` 与一份最终对象确有异步的普通输入。先存 ordinary 对象、配置、数学与机制清单；不运行扩量资格。
2. 对循环自动插桩，改变 runtime K 并保持同 binary。保最终函数/基本块/读钟及 logger 位置、纯计算依赖、实际 raw 端点和原数学输出；首末 program 各核真实 writer 及提交，不以 host header 作证。
3. 核 publisher/storage/launch 组合与指针单位、最大写入范围、发布字段、guard 和 owner 完成收据；错组合在可知阶段拒绝。完成后解码失败仍保 bytes/关联快照并安全释放；初始化中途异常不提前释放潜在写者资源。
4. provider 从真实 getter/目标证据给本地单位及独立窗口；用共同整数换算/SQL 检查实际端点。没有源边界/精度的 counter bracket 只过局部单位门。
5. 异步样本核 submit/group/wait 覆盖及两代实际物理复用；ordinary/疏/密三方检查关键依赖与 in-flight 机会未被新同步破坏。先证明语义与所需域间比较，再画时间 flow；不把 observer overlap 当硬件引擎 overlap。
6. 同 raw 从新进程离线重导两次，再以合法补证形成新派生身份；原件/旧报告摘要保持不变。注入输出后索引前失败及并发 proof，核无半成品索引、无应用重放。
7. 各最小链 C/P01 闭合后再进入既有独立数学/UI/最终三名代码 reviewer；任何步骤只通过合同 fixture 时明确标注，不填设备门通过。

以上路径在既有三后端 Docker、原测试 P/E 与现有 bundle 内即可执行。无需新增第四芯片、先建设统一设备 IR 或增设另一套状态台账。

## 有限复核：本轮文档修订

只复读本次变动的测试 §4、设计 §8.14 与测试 §8.9；未扩大源码检查、未执行设备或产品测试。

- **P2-1 已闭环**：测试 §4 明确保留原始 modulo tick，仅唯一展开后的坐标/导出 ns 要求 end≥start，并保当前 schema 的拒绝语义。与设计 §8.12 和既有合法回绕用例一致。
- **P2-2 已闭环**：设计 §8.14 给出 binary/function/section、读钟/marker 机器位置、区域范围/基本块、控制路径/循环、依赖约束及未覆盖情况；明确公共 validator 与后端模式检查器分工。测试 §8.9 对应真实对象及缺字段 fixture，未将任意机器语义证明强加给公共层。
- **P2-3 已闭环**：规则身份绑定已安装实现的稳定内容/构建指纹；测试明确“公开版本文字不变但实际实现指纹变化”仍生成不同派生身份，规范编码排除非语义变化。人工漏升版本的路径冲突已有可执行验收。
- 对同节新增输入闭包、canonical revision、完成收据及有界锁，仅检查其与上述三项的关系：它们分别保存边界/规则证据、保留旧解码结果、避免半成品及并发丢失，未发现新的编译证据或版本语义冲突。

复核结论：本次三项设计建议均已在文档层闭环，维持“设计合理、可按最小纵向链实施”的结论。R1–R3 的真实边界/流水、物理代际、发布及 clock 风险仍须原定设备实证，不因此取得代码或任何设备资格。
