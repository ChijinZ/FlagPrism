# 时间线设计独立评审：可移植性与整体可行性

评审日期：2026-10-18。结论：**有条件可行**。本报告只作设计评审，不证明任何设备、默认入口、时钟、异步机制或 Perfetto 门已经通过。

评审范围：通读 `Profiler/docs/timeline_design.md` 与 `timeline_testing.md`，重点设计 §0.5、测试 §0.2，并检查与源边界、记录、生命周期、时间资格、异步、版本和实际 UI 要求的一致性；只读少量实际 Python 源码核对接口落点。未连接服务器，未 import 产品、运行测试/编译/设备/UI，未修改产品或论文，未读取其它本轮评审报告。

## 整体判断

五类部件按变化原因划分合理。compiler、transport、decoder、clock、mechanism 各自的复用条件不同，设计没有把同厂商、同 SDK 或同 getter 当成全套资格继承。§0.5 正面承认当前 owner/hook 仍有 NVIDIA 调用形状，并把它列为需要通过真实第二、第三调用者修正的实现边界，比提前承诺稳定插件 API 更可信。新增普通算子、新型号和新执行模型分别处理，也能避免逐算子 adapter 和“一个 decoder 就能移植”的误导。

公共抽象保留 observer/program/operation/resource 区别、M:N 来源、group/wait 覆盖、物理 slot/flag 与 generation；允许不同事件数量和多 mapper，且影响判断的字段不能藏在 extensions。因而不会天然抹掉异构细节。公共 validator/exporter 不解析厂商 ISA；具体 ISA/SDK 语义仍由后端负责，这一信任边界是必要的，公共引用检查无法替代它。

从 raw 到 canonical，再到分别有资格的时间/依赖视图和同一个 Perfetto 消费链，方向合理。单位、区域边界、epoch/误差、动态关联分开授予，能避免现有 counter-ns 局部成功膨胀为完整时间线。§8.14 的不可变输入闭包、canonical revision、内容身份与离线升级也支持未来修正 proof/decoder 而不重跑应用。

不过，全量可行性仍取决于三家最终对象边界、发布协议、时钟可比性与真实物理复用是否可取得。文档已经承认这些风险，并设置 A/B→完整 P01→独立资格；不能据本次职责划分合理便保证三后端最终交付一定可完成。不存在足以据文档判为“不可行”的架构矛盾，也没有证据支持已经实现低成本第四芯片接入。

## 按严重性列出的问题与风险

### 高：自动边界检查器是实际可用性的核心前置条件，尚不能从现有机器映射推导出来

位置：设计 §0.5 第87行、§4、§8.11、§8.14 第530行；测试 §0.2“普通算子无需人工批准”、P03。

这是明确的实施/取证风险，**不是文档声称已完成的缺陷**。要求在每次实际 binary/site/path 上自动授予通用结构资格，工作量远高于记录 PC 或核对 marker。当前只读落点 `timeline_nvidia_machine.py` 中 counter-map 明确把 source-region、participation、completion 证明分开；`timeline_views.py` 的已有实现也显式保持 source boundary/precision 未证。现有代码形状因此没有推翻文档，但也没有实现该新增承诺的证据。

最小动作：每后端先选有依赖 runtime-K 循环，固定一条可支持的通用 lowering 规则；自动产生本次 binary/function/section/region/path 收据，证明 begin/end 与目标运算依赖及控制路径，而非人工填范围。对同结构不同源码自动复用，再遇陌生结构明确未证。任一后端做不到时，停在相应部分资格，不进入完整 P01/独立矩阵。不能把人工分析每个 kernel 固化为公开工作流。

### 中：新增自动检查器的验收仍缺一个明确的“范围合法但语义错误”拒绝用例

位置：测试 §0.2 第45–48行、§8.2“编译边界”、§8.9“证据收据与撤销”；对应设计 §0.5 第87行与 §8.14 第530行。

现有要求覆盖真实正例、错 binary/site/范围、缺字段和陌生形态，但这些主要检验绑定/结构完整性。一个检查器可能生成字段齐全、PC 合法、身份正确的收据，却没发现纯运算越过读钟、条件路径绕开端点、或后续优化破坏依赖；再由公共层核引用仍会通过。文档已要求最终对象核顺序，但自动化承诺应有针对检查器错误接受的可执行拒绝判定，避免只验证“自动生成了收据”。

必须补充的最小验收：针对实际支持的一个通用模式，保留明确标注的离线机器/控制流 fixture 或测试对象，使算术被移到读钟外，或一个合法分支不经过所声明端点；保持字段/身份/地址范围自洽，由后端检查器实际拒绝或未证。再用相应合法模式证明非一律拒绝。fixture 仅检验规则，不替代真实最终对象正例，也不要求建立任意机器码证明器；可复用既有 P03/P10，不增加独立数学数量。

### 低：旧交接表把 clock proof 写进解码输入，容易与新独立 decoder 合同混读

位置：设计 §8.7 第312行“解码与机制映射：raw + manifest + 本次 clock proof”；对照 §0.1、§8.9、§8.12 与 §8.14 第526行。

按后文解释，这一行可以理解成编排动作，所以不是实质架构矛盾。但表内同时写“后端处理位宽”和“公共层核可比较时钟”，后来实现者可能把 provider 又揉进 physical decoder，损害新型号按部件复用和纯离线重解码。

建议将该行明确标为“解码/机制/时钟编排”，或拆成物理解码与资格组合两个子动作，并注明 physical decoder 无 clock proof 也能输出 typed raw batch。无需新接口或新测试框架。

这些最小验证已经大体能映射到 P01–P10/E/C；其中没有一个可用本报告补齐。

## 验收是否可执行

**可执行，但尚待实现和真实执行。** 测试 §0.2 能发现伪造 CUDA 值、逐算子规则、型号资格误继承、公共层读厂商 raw，以及“三个 adapter 但实际入口未通”。§8.7–§8.9 对默认与 advanced、真实设备与 fixture、输入闭包、重导失败、并发提交收据、预算、未知 completion 的区分，也给出了实际输入、动作和失败判定。已有六个独立数学可承载新增检查，不必再扩算子数量。

要保持验收可操作，应将三份接入清单落实为具体函数、安装内容身份、命令、产物和未满足项；不能只填抽象名称。当前源码只读核对确认 `TimelineOwnerPool.prepare` 仍有 `function/stream/num_ctas` 及整数 stream 检查，hook 初始化/指纹仍引用 NVIDIA，实现修正是合理必要的工作，不能靠参数改名判通过。公共 `timeline_views.py` 和 `timeline_perfetto.py` 已有隔离单位视图及重新核 provider proof 的落点，可作为先接 SQL 的起点；它们不证明多后端区域/时钟/异步已闭合。

## 必须修正与非阻断建议

必须修正：为自动边界检查器补上述语义错误接受的负例及明确判定，避免新 §0.5 的核心能力只以收据字段和正例验收。实施放行必须实际闭合自动边界、发布/owner、时钟与物理复用；这是完成 P01 的必要条件，不能以评审结论或现有 raw/counter-ns 结果代替。

非阻断建议：澄清 §8.7 的编排/physical decoder 用语；每份接入清单列“复用实现、复用证据、重新取证、替换实现”四种实际工作，区别复用代码与继承设备资格。先用三后端真实 diff 和回归说明边界有效；将第四芯片工期、固定 LOC 或“只加配置”留为未验证，不作成本承诺。

## 自动边界检查器的有限实现路径

合理的首版无需求解任意 ISA：compiler hook 为少量通用控制结构保留有来源的 site/执行映射和依赖说明；后端检查器在实际最终对象上定位函数/代码段，检查所支持的读钟模式、目标指令/基本块及必要依赖，核入口/出口路径和循环回边；只对匹配规则的实际 site 发收据。优化产生融合时保 M:N，不将同一段成本复制成多个区域；不识别的 helper、分支或调度形态给出具体未证原因。规则复用按通用 lowering/控制结构与工具链条件，仍检查每次 binary 绑定，不能以 kernel 名称/hash 为规则。

这条路径与 §0.5/§8.14 的条件化检查相容，属于可逐步实现的工程路径；但首版支持范围必须在冻结前写清，最终未见数学触发陌生结构仍计产品缺口，不能用“有限规则”作为事后缩分母。建议将检查器首个最小规则及上述正/负例入口记录在现有后端接入清单中，避免另外建设通用 ISA 平台或重复台账。

## r12 修正后的有限复核

复核日期：2026-10-18。只读本轮修正涉及的设计 §0.6、§8.7 和测试 §0.2，保留以上初审原文；未执行产品、测试或设备操作，也未读取其它评审。

**本报告提出的文档问题在设计层关闭。**

- 自动边界语义负例：测试 §0.2 现明确构造身份/格式/PC 范围自洽的运算越界、循环外提/出口绕过、caller/site 错关联和 wait 覆盖改变，并要求实际命中后端语义规则、给具体原因且通过合法对照，排除了只靠 parser 拒绝或一律拒绝的假成功。初审“中”问题已关闭。
- 有限实现路径：设计 §0.6 按有依赖直线区域、runtime 循环/条件路径、原 wait 三类通用结构给最低检查谓词、失败资格和规则版本/条件冻结；helper 调用点、observer/predicate、原协作依赖与未知结构都明确处理。它不要求通用机器码证明器，也不允许按算子身份或新增同步补资格，且不缩最终验收分母。初审高风险已有合理、有限的实施入口；风险仍须通过真实实现和取证消除，不能在此标为实现通过。
- decoder/provider 边界：设计 §8.7 旧表已改为“解码/机制/时钟编排”，明确 physical decoder 无 clock proof 依赖，provider 和 mapper 分别提供事实，再由公共层授予资格。与 §0.1、§8.12、§8.14 一致，初审“低”问题已关闭。

整体仍为**有条件可行**，本次有限复核没有新增设计阻断项。三后端自动检查器、真实发布/owner、时钟及物理复用的设备证据、公共 SQL/UI 和最终代码审阅继续待实际验收；上述文档关闭不增加任何设备资格，也不量化第四芯片适配成本。
