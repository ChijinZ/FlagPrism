# r12 独立设计评审：编译插桩、普通新算子与边界自动取证

## 评审范围与结论

**结论：有条件可行。** 新设计 §0.5 和验收 §0.2 的方向合理，与后文的资格分离、三后端实证、陌生结构保 raw、逐项失败留存基本一致。五类部件按变化原因划分，不强制统一物理 ABI 或 CUDA 主体树；实际调用后再抽取公共代码，也比预建完整插件平台可实施。

条件集中在自动边界资格的最后一步：文档已规定“应自动检查”，但首批可接受通用结构的放行判据、observer 参与范围和对应错误语义反例还不够明确。应将下面的最小规则与负例补进现有 P03；无需建设任意机器码证明器，也无需增加独立资格数学数量。

本报告只读两份指定文档及少量相关代码，没有连接服务器、import 产品、执行编译/产品/测试或读取其它同轮报告；仅新增本报告。设计评审没有取得任何设备、时钟、边界、发布、SQL/UI 或最终代码资格。以下代码观察只说明当前静态落点，不代替安装及真实执行证据。

## 按严重性的问题

### P1：自动边界检查尚缺首批通用模式的最小放行判据

位置：设计 §0.5 第 87 行、§4 第 156 行、§8.11 第 448 行、§8.14 第 530 行；测试 §0.2 第 45 行、§8.6 第 276 行、§8.9 第 337 行。

现文已正确要求最终对象、控制路径、依赖约束和本次 binary/site 绑定，也明确 noinline、volatile、memory clobber、正 duration 都不足。问题是“后端核支持的通用指令/控制模式”尚未说明最小核验内容：何时可以认定纯算术未越过读钟、出口覆盖哪些执行路径、helper 的读钟如何归属于每个 caller。只把指令位置列入收据，仍可能把一次人工判断机械化成自动填表。

建议将首批模式限制为实际可实现的三类，并在每后端明确具体等价判据：

1. **有依赖直线区域**：机器对象中识别实际 begin/end 读钟或其精确调用点；支持指令的依赖链使声明范围内的计算不能移到 begin 前或 end 后。load/compute/store 按实际依赖与访存语义检查，不因 logger 有副作用推定所有算术已受约束。不能证明完整源区域时缩小所声明的合法区域或保持 counter bracket，不能凭源码行包围关系放行。
2. **运行时循环**：识别循环头、回边、出口和读钟所在路径；每次已声明 body 路径都经过对应读钟，不能把 hoisted/sunk 的读钟当每轮边界。相同 binary 的 K 变化与实际 occurrence 只作动态交叉检查，不独自证明机器边界。
3. **原有异步 wait**：识别实际提交、原 wait 及其覆盖规则；读钟包围的是 wait 的观察者区间，完成 checkpoint 只授予原 wait 所保证的范围。不能因 wait 前后有读钟就推断精确 engine begin/end。

分支、多出口、predication、多函数、无法识别的控制流或指令先明确支持范围；出现未覆盖路径给具体未证原因。规则由结构/指令语义选择，不得由算子名、source hash 或维护者手填范围选择。各规则应带版本、目标条件和未覆盖项，再由本次对象生成收据。这里要求小而闭合的检查器，不要求覆盖任意 ISA/控制流。

**影响与失败路径：** 不补这一层，普通新算子“无需人工批准”仍可能停留在设计口号；补齐后，陌生结构 raw-only 的失败路径已经明确，技术上可以渐进实现。

### P1：验收应直接攻击边界规则的语义，而不只攻击证据绑定

位置：测试 §0.2 第 45–47 行、§8.5 第 262 行、§8.6 第 276–277 行、§8.9 第 337 行。

现有错 binary/site、缺字段、PC-only、错范围等负例有价值，但没有明确要求：**收据字段、身份和引用全部合法时，检查器必须识别错误的机器顺序/路径。** 若公共层与后端只互相核字段，错误 checker 仍可能生成格式完全正确的合格收据。

必须在已有 P03 中复用少量 CPU 合同 fixture，或离线解析用的对象/反汇编 fixture，加入以下正反对照：

- 保留 marker 和 timer 映射，移动一条声明区域的关键算术/访存到边界外，拒绝对应源区域资格；
- 将循环内 begin/end 提到循环外，或使一个合法出口绕过 end，拒绝相应循环/路径资格；
- 保留 helper/callee 本体，把一个 caller 的 site 或路径错关联，不能授给另一 caller；
- 保留原 wait 的位置但改变 wait 覆盖集合，不能继续授予原完成/依赖结论；
- 保留正常同类结构作对照，并验证普通新源码无需修改规则即可生成收据。

这些 fixture 不执行危险设备代码，不证明某设备真实出现过变换。实际最终对象正例仍由每后端普通循环、归约/矩阵及真实异步样本提供。若某 fixture 的改动破坏输入格式，应另保一个格式合法、身份完整但语义错误的版本，避免只测到 parser 拒绝。

### P2：边界收据应显式绑定“谁的经过时间”，避免代表性写者扩张成整个协作主体

位置：设计 §3 第 136–137 行、§4 第 147/156 行、§8.2 第 250 行、§8.14 第 530/534 行；测试 §0.1 第 30 行、§0.2 第 48 行、P03/P04。

文档区分 program、observer、operation、resource，是正确基础。但首末 program/observer 身份正确，不自动证明某个被选中 lane/标量写者的时间覆盖整个协作区域。尤其归约、predicated SIMD 路径、auto-blockification 或多主体消费时，begin/end 两端可能参与者不同，或只有代表性写者经过所声明路径。

应在边界收据写明实际读钟主体、参与/predicate 条件、两端同一 observer 的依据，以及若声称覆盖协作区域，原程序哪些依赖/同步保证该覆盖。不新增同步；无依据时只标该 observer 的 bracket。P03 加一个正常协作结构和一个参与条件不一致的 fixture，检查不会扩大资格。这可复用已有归约/矩阵样本，不增加数学数量。

## 整体设计合理性与实际落点

- **编译与新算子：** 逻辑 source region 与实际执行 site 分离，M:N 映射、融合不复制 duration、消除不造事件的要求合理。通用规则覆盖新源码而非逐算子 adapter，是可持续路径；不能承诺所有普通可运行 kernel 立即都有已证区域时间。文档将 ordinary 成功而 profile 失败保留为产品缺口，没有用 unsupported 改分母，合理但意味着完整交付仍有实际工程风险。
- **公共运行时与后端差异：** admission、唯一调用身份、预算、潜在写者生命周期可共享，executable/context/queue、发布和完成语义由 transport 保留。§0.5 已识别 NVIDIA 耦合，不能把现有签名当稳定合同。先有第二调用者再抽取，没有明显实施障碍。
- **发布与生命周期：** owner 在异步初始化前接管完整资源，完成、readback、持久化、decode/export 分离，坏 guard 也留存已经取得的 bytes。这些规定能防止“异常即释放”及“解码失败丢其它调用”。实际资源所有权与初始化/D2H 异常仍必须逐阶段实测。
- **时钟与异步：** 单位、边界、epoch、动态关联分别授予资格；逻辑 group 不冒充物理 generation；不向用户 kernel 注入完成 barrier。这样不要求三后端统一微架构，但每后端两代真实复用及所需时钟比较是尚待实证的硬门。
- **离线和展示：** 原件/输入闭包、canonical revision、proof 内容指纹及幂等派生，足以承载补证而不重跑应用。共同 validator/exporter 加真实 Trace Processor/UI 的分层验收合理。文件事务、索引、锁等工程范围较多，应复用现有存储代码，避免先建独立平台阻塞最小纵向链。

静态代码核查支持“尚在实现”的文档口径：`timeline_nvidia_machine.py:351–363` 返回 `counter_mapping_complete_region_unverified`、`region_boundaries_verified=False`，保 function ranges/call sites 但没有冒称源区域已证；`timeline_events_nvidia.py:154` 与 `timeline_events_enflame.py:186` 仍标 boundary unverified。`hooks/timeline.py:139–161` 的 fingerprint 明确依赖 NVIDIA driver/decoder；`timeline_runtime.py:97–121` 的 prepare 仍有 function/num_ctas 等参数。这些是需要沿真实后端调用重构/补齐的落点，不是现有公共适配完成证据，也不能仅凭这些代码断言其它设备不可行。

## 验收是否可执行

**总体可执行，但边界自动化的 P03 需要上述最小补充后才足以验收“无需人工批准”。** §0.2 已要求独立 qualifier 的未见源码、实际规则收据、真实三后端消费者和错范围 proof；与六个独立 kernel、冻结规则及失败后的通用修复流程相容。当前验收能发现“类名统一但默认路径未通”：它要求公开 API/CLI、真实 writer/guard、终盘重读、同一 SQL/UI，以及 per-invocation 失败终态，不能只提交 adapter 清单。

不能将“陌生结构可以 partial”解释为资格豁免。对冻结的 ordinary 合法样本，边界未证、时间缺证或异步未闭环仍按对应门失败。§0.5 的工程退路与完整资格门并不矛盾，但执行报告必须同时保留这两种状态。

本轮未见不可行的架构性矛盾，也没有足够依据承诺三后端全部硬条件一定可达。GCU/Ascend 的时间/异步可观测性、NVIDIA 插桩后的关键流水保持仍是最小纵向样本需要解决的风险，不能由设计票数消除。

## 必须修正与非阻断建议

必须修正：在现有 §0.5/§8.14 与 P03 中明确首批通用模式的放行/拒绝条件，加入身份完整但语义错误的机器边界反例，补明 observer 参与与覆盖范围。以上均可直接复用开发样本及合同 fixture，不要求新增设备、独立数学或通用 ISA 平台。

非阻断建议：将 §8.1–§8.14 反复出现的资格、组合、owner、派生版本要求维护为一个规范锚点加交叉引用；接入清单保留规则版本、真实调用者和失败理由，避免以后多节重复文字漂移。给机器检查器单列有界解析/工具耗时预算，并计入已有冷编译/导出预算；超预算应留存产物并报告对应失败，不以人工审批替代自动路径。
