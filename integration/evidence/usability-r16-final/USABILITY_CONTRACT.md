## 2. 如何理解“通用”和“细粒度”

### 2.1 支持边界按编译能力定义

输入是通过已安装 FlagTree 支持路径编译的用户 Triton 算子及其普通启动脚本。当前必须落地的硬件是 NVIDIA RTX PRO 6000、燧原 ZIXIAOC200 和昇腾 910B4-1。其他输入语言/设备可以增加，但不能用增加后端数量替代这三者的可用性。

启动时明确支持的编译路径、SDK/架构及 IR 特性范围，包括普通访存、逐元素计算、归约、矩阵计算、融合、循环、尾部 mask 等。范围按真实编译能力审计，不能定义成几个算子名称的白名单；不能在 profiler 失败后悄悄缩小范围。

对当前后端原编译器就无法编译的程序，保存未插桩编译失败证据，归为前置条件不满足。对未插桩可运行且属于声明特性范围的程序，profiler 失败或只有空泛输出就是本轮缺陷，不能改记 unsupported 让验收通过。

### 2.2 基本模式必须无需修改算子内部代码

用户应能用一个公开 CLI 入口运行自己的脚本，或在外层使用公开 session API。基本模式自动发现可观测对象、生成采集计划并输出结果；不要求用户先手填 site ID、读 LLVM、指定 ABI 形参、修改厂商编译文件或给每个 kernel 加 scope。

保留显式 scope、手动选择 site 等高级模式，但不能用它们代替基本模式验收。新增入口的准确名称由实现决定；最终必须有可复制的真实命令，不在文档中把未实现的 API 写成已有功能。

### 2.3 最低细粒度输出合同

对验收集合中具备多个内部操作的非平凡算子，默认模式至少提供：

1. 实际调用、编译配置、二进制、program/执行实例及后端执行主体。
2. 自动枚举并标识内部观测位置，关联有效的源码位置/区域及编译操作。优化后无法唯一归属时保留候选与原因；不能所有位置都只有不可解释的匿名编号。
3. 真正在设备上产生的内部动态信息。通常至少两个不同内部位置；运行时循环还需体现同一位置的多次访问及实际数量。单个最小操作程序的例外要有结构依据，不能把复杂程序都标成例外。
4. 每类记录的含义，例如源控制区间、发射、等待、检查点、执行计数或原生计数器；明确时间单位、时钟范围及是否可比较。
5. attempted/committed/dropped/sampled 等适用状态，或该协议确切对应的损失信息；区分未执行、未采集、丢失、不支持和采集失败。
6. 在报告中直接从源码/操作定位相关动态记录，查看实例、重复次数、原生任务及执行组织；基本使用不需要用户自行解析 IR、SQL 或十几份 JSON。

**只有整核时间、静态 IR 清单、算子名称、预填的示意图、空报告或全部 unknown，均不能算基本细粒度采集通过。** 时间精度不足时可以输出真实的检查点、计数或局部 ticks；不得假装这些是精确未插桩成本。仅有未经关联的任意计数也不足以满足上述合同。

“管用”的必达部分是回答：哪些源区域实际执行了、由哪些主体执行、重复情况如何，以及有哪些可用的局部活动/依赖信息。对有适当硬件支持和证据的情形继续提供时间与计数器分析。自动诊断根因或自动优化不是完成基本 profiler 的必要前提。

## 3. 不能逐算子适配

- 产品代码不得根据算子名、用户文件名、某个测试形状、固定 SSA 编号、Study 二进制 hash 或历史 site 29 切换算法。
- 不得为新算子增加专用 LLVM 文本替换、硬编码 actor/缓冲区、手工导入时间表或人工填报告。
- 如果遇到新算子失败，首先定位到 IR 操作类别、控制流、数据布局、源信息传播、后端原语、运行身份或记录协议。修复必须作用于这一类结构，并用另一个不同算子验证复用性。
- 真实编译符号和二进制 hash 可用于身份关联；禁止把这些身份当成已知算子的功能白名单。测试可以有算子名字和数值 oracle，但不得依赖隐藏的产品专用分支。
- 逐算子增加测试是正常工作；逐算子增加产品特判不能作为通用性达标。

## 4. 需要推进的工程链路

### U1：发现与计划

- 将源码/IR/执行结构库存作为正式公共能力；消除必须先运行现有案例、找到 site ID 再来采集的依赖。
- 尽可能在真实参数触发的编译过程中提取库存并自动选择区域。发现阶段可以编译，但默认不能额外执行用户 kernel 或自动重放整段应用；有副作用的脚本只能按用户请求执行。
- 保留稳定的逻辑观测标识，并绑定实际 specialization、编译阶段及最终位置。不能从一个二进制直接搬用 site 数字到另一个二进制。
- 采集计划应可查看：选中了什么、为什么、实际插入什么、预算是什么、哪些未覆盖。调节默认参数属于通用策略，不能来自特定算子的已知答案。

### U2：覆盖通用 IR 与后端执行语义

- NVIDIA 增加无显式 scope 的基本采集路径；原有手写 scope 继续作为高级能力。
- 燧原让库存发现、自动选择、完整记录发布和源关联通过默认入口工作。解决全量 scalar 膨胀、vector 替代高成本的问题；不能让用户碰巧选择正确 publisher 才成功。
- 昇腾扩展目前主要覆盖 wait/set/循环头的路径，使普通逐元素、访存、归约及计算区域也能获得符合最低合同的内部动态信息。不能因为不存在某个同步原语就只有整核结果。
- 支持特性通过前端/中间 IR 与后端通用机制组合实现。必要时改 FlagTree；不能把厂商 SDK 的黑盒信息缺失伪装成已经观测到。
- 对异步计算、搬运和同步保留原有执行语义。不得默认插完成屏障后把改变的程序当作原程序，也不得把发射区间称为硬件 busy。

### U3：默认模式与工程预算

- 默认选择应在设备端或编译阶段真正减少采集工作，不能只裁剪导出结果。区分采集预算、记录预算与展示过滤。
- 提供安全的默认容量、选择、采样及编译/导出超时；精确记录覆盖与丢失，必要时提供从较粗观测到更细观测的公开操作。
- 基本默认模式必须直接通过验收；不能用全量模式失败后的一串未记录专家参数证明“可用”。确需高级模式时，文档和报告必须说明条件与代价。
- 先测量既有问题，再实现通用改进：编译膨胀、重复复制编译/SDK 产物、host 同步、逐事件处理及重复导出等。不要只把 buffer 缩小就宣称解决成本。
- 验收采用明确的初始工程预算：小型资格样本默认插桩冷编译超时为 `max(120 秒, 3 × 同设置下未插桩冷编译时间)`，上限 300 秒；缓存已具备后的单次导出超时 60 秒；单 kernel、至多 10 次选中调用的默认完整 bundle 目标不超过 64 MiB。这些是本轮产品门槛，不是行业标准或 GPU 时间精度保证。保存每项实际值。
- 不得为隐藏超时/超量失败静默放宽上述门槛。若 SDK 原生采集本身就超过某门槛，先用独立原生最小实验量化，再实现可用的正式轻量默认路径，或报告具体未完成项；不得删原始必要证据凑体积。可按合同去重并引用相同的原始产物。
- NVIDIA 独占性能/开销基准继续按用户此前要求暂缓。允许功能编译、短 GPU 正确性检查及防卡死的超时；不开展 NVIDIA 设备延迟对比、吞吐或低开销认证，不触碰其他用户任务。不能以此跳过 NVIDIA 基本功能和安装验收。

### U4：源位置、身份、时钟与报告

- 保留既有 provenance、原始 bytes、唯一候选约束、调用身份及丢失检查；修复新路径时不能退回名称/时间邻近匹配或比例拉伸。
- 源信息丢失需要优先研究通用传播机制，不以“论文允许 partial”作为停止实现的理由。仍然无法恢复时，明确说明哪些位置可定位、哪些不能，并让用户能继续使用其余有效信息。
- 面向用户提供源码/区域视图、执行主体/依赖视图及动态记录/计数视图；呈现与当前后端相符的真实信息。报告只显示已核验的时间轴，不把不同 replay 当作同一次执行。
- 跨 actor 时钟、动态 buffer/iteration/flag generation 关联等能力，按真实使用需要推进，不因论文未写而排除。缺硬件/编译证据时不能编造；基本信息模式仍须有可用输出。最终明确这些能力的实际完成程度。
- 错误要给出用户可操作的定位：哪个编译阶段、IR 特性、位置、SDK/版本或请求参数不支持，保留失败产物及原应用异常。不能把空采集标成成功。

### U5：安装、入口与交付

- 三后端分别提供从明确源码版本/安装包开始的可复制安装和快速开始。所需 FlagTree 修改以可复现 commit/patch/构建集成管理，不让用户逐文件手工打补丁。
- 验证独立安装环境的真实导入位置、native/插件/头文件和 ABI；禁止依赖原热补丁目录、隐式 `PYTHONPATH`、旧缓存、未写入文档的私有文件或源码 fallback 才成功。
- 允许使用环境中已有且版本匹配的 Torch、SDK 和经过核验的编译器发行物；新增或修改的 pass/native 模块必须按文档从干净的项目源码构建，并实际安装测试。不要把复用旧库的 wheel 重新打包当成新增 C++ 的构建证明。
- 提供版本/环境诊断入口或等价命令、一个默认 profiling 命令、一个报告打开/导出入口。基本流程中的手工参数和内部知识应尽可能减少。
- 保持旧公开接口和已有正确性合同；必要的 schema/接口变化必须明确版本和兼容/迁移行为。

## 6. 验收不是再挑几个成功案例

### 6.1 测试集合与冻结规则

1. 旧六算子、RMSNorm 及机制测试继续作回归，不能充当未见算子验收。
2. 建立开发集合，覆盖逐元素/融合访存、归约、矩阵计算/生产消费、动态循环、分支、尾部和布局变化。它用于工程调试，明确标为开发数据。
3. 另由独立使用者/验收 agent 提供至少 6 个未参与本轮产品调试的数学 kernel：逐元素/融合访存、归约、矩阵/融合计算三类各至少两个。使用不同于旧案例的数学表达与源码，不接受仅改名字/shape。
4. 每个验收 kernel 每后端至少两种 shape（至少一个有尾部）、两种合法配置。先对同一源码做未插桩基线，冻结代码、输入、容差、配置、预期内部结构及清单 SHA。配置可符合各后端编译约定，不能改写数学算法迎合 profiler。
5. 基线就不能编译/运行的组合单独报告，不计 profiler 成功；事先准备并记录替补。已通过基线、但 profiler 失败的组合禁止替换掉、降低门槛或排除。
6. 完整验收开始前冻结产品代码、默认配置和公开文档。工程 agent 不为验收源码添加特判；记录实际暴露范围，不虚称完全盲态。
7. 首次通过率与通用修复后的通过率分别报告。失败后修通用机制、补同类回归，再冻结验证。修复用过的 kernel 不再叫未见样本；泛化收尾增加独立的新 kernel，至少涉及修复触及的结构类别，不能不断复用已知案例宣称通用性。

### 6.2 黑盒端到端通过条件

独立使用者只拿公开工具文档、受支持环境和自己的普通脚本，从独立安装环境开始，运行默认入口。禁止 profiler 私有 API、预填 site ID、事先已采集的库存、手工修改 LLVM、临时源码 patch 或维护者私下提供参数。

每个组合必须同时满足：

- 未插桩与默认采集均完成；原数值容差、输入不变和输出 canary 通过，不能因插桩放宽容差或改数学。
- 达到第 2.3 节的动态细粒度合同；源码/编译位置、调用和观测实际可追溯，非 native-only/静态-only fallback。
- 普通启动脚本只执行用户请求的次数；有副作用计数器/状态检查可证明没有隐藏重放。
- 两个不同 specialization 的位置与二进制关系正确；重复调用互不串联。动态循环用运行时输入改变次数，并验证二进制确实相同，避免 constexpr 重编译冒充动态行为。
- 尾部/分支未执行的位置能解释；丢记录和未执行可区分；默认集合不允许靠严重丢失把记录压小后宣称完整覆盖。
- 用户能直接在报告中找到内部位置、执行主体和动态结果；不需要手工拼接 JSON 才知道这次采到了什么。
- 默认编译/导出/体积预算有实际测量并通过。体积和超时测量是工程验收，不是 NVIDIA GPU 性能基准。
- 多次独立运行以及冷/热编译状态均可复现。所有结果附实际 source/native/plugin 版本与 hash。

### 6.3 代码质量与测试要求
