I did not read the live implementation journal, earlier reviewer reports/dispositions, reviewer status, or peer outputs, contact other reviewers, access experiment servers, install software, or modify submitted code/paper. **Judgment:** a plausible OSDI Operational Systems contribution exists: trustworthy selective operator diagnosis across compiler/SDK boundaries, demonstrated through concrete publication, provenance and invocation-association failures and repairs. Functional usability is supported on the pinned environments, subject to substantial and explicit restrictions. Diagnostic usefulness is supported for the cooperative mapping clue and the first producer-granularity intervention. I would request major revision before submission readiness; I found no demonstrated blocking correctness defect in the supported final path. This is not a prediction of acceptance.

The official [OSDI 2027 CFP, Submission Tracks](https://www.usenix.org/conference/osdi27/call-for-papers) allows Operational Systems work that expands systems knowledge through implementation, analysis and experience; novel research ideas are not mandatory. It does not impose a production-user quota. Three research machines therefore do not automatically disqualify this contribution. The outstanding significance question is whether these concrete failures teach enough beyond careful adaptation of existing profiling machinery. The candidate has credible material to answer that question, especially the logger ownership counterexample and local-wait sensitivity result; counting adapters or tests cannot answer it.

## Supported contributions

1. **M1 is an actual partial program-to-execution mapping, rather than just a common schema.** `Profiler/python/flagtree_profiler/execution_ascend.py::build_execution_mapping` imports actor/site inventories, retains original LLVM evidence and distinct source candidates, and gates source associations on verified compiler provenance and the tracked source table. `ascend_hivm.py::validate_compiler_provenance` checks retained source/manifest bytes, hashes, typed JSON serialization, enclosing compilation and finished actor job identities. `build_static_readiness` requires the exact graph-sync-solver stream and a unique matching actor inventory. This supports the fresh bundle's one static channel and partial origins. It does not establish dynamic flag generations or exclusive cost ownership. The manuscript's 34 unique/27 ambiguous/13 unassociated origin counts are appropriately bounded.

2. **M2 contains a concrete correctness repair.** `Debugger/lib/Instrumentation/Passes.cpp::emitDynamicTimelineStores` places publication under the sole-writer branch and uses scalar record words by default. `storePerWorkItemRecordVector` repeats full record values and offsets in each ownership slice for the alternative mode. `Debugger/python/flagtree_debugger/compiler.py` freezes publisher mode and actual work-item configuration; `Profiler/test/test_enflame_publication_hardware.py` checks 1/4/8 work-items and scalar→vector→scalar cache behavior. This addresses the real possibility of numerically correct kernels producing incomplete trace records. Post-synchronization tag checking is a reasonable contract; it is not claimed to be a concurrent release/acquire protocol.

3. **Ascend instrumentation respects a meaningful semantic boundary.** `Profiler/llvm/AscendLateObserver.cpp::instrumentActor` brackets existing primitives, records loop-header checkpoints and selects semantic classes before adding timestamps. It does not insert a completion barrier. `appendRecord` uses exclusive actor segments, separate attempted/committed/drop fields and unknown sentinels for iteration/buffer identity. Program selection gates memory publication, while selected counter reads can execute elsewhere. `observations_ascend.py::decode_dynamic64` checks header arithmetic, actor/occurrence consistency, selected program and authoritative site semantics. These details substantiate the paper's narrow issue/wait/control interpretation.

4. **M3 crosses the actual worker and native context boundaries.** The bridge in `integration/patches/ascend/patch_launch_receipts.py` queries last task on the actual worker immediately after launch, before the other SDK queries. `CannProfiler.cpp::publishReceipt` and `closeReceiptCapture` serialize acceptance, retain cancellation/duplicate/late states, and avoid overwriting closed-epoch payloads. `cann_joint.py` seals the capture, joins exact worker/connection tuples, uses context membership and compute `globalTaskId`, and rejects collisions. `cann_native.py::_verify_dispatch` rechecks complete dispatch views and unique compute membership; `_verify_source` rechecks raw receipt ownership and launch/binary identity. Task zero is accepted on successful queries. This is substantially stronger than matching names, nearest timestamps or a caller's last-task value.

5. **Raw recovery and clock failure semantics are implemented.** `profile.py::_export_native_observations` writes and fsyncs a recovery journal before sidecar merging, atomically replaces the sidecar, and acknowledges queued captures only afterwards. `_snapshot_cann_launch_receipts` separately journals drained receipt bytes before source augmentation; all-storage failure explicitly reports that durable recovery failed. `cann_source_clock.py` requires exact invocation/binary, recompared native proof, actual compiled SYS counter evidence and sealed frequency evidence, and adds duration conversion without shared origins. `reconstruction.py` groups identities without stretching intervals into task envelopes. Recovery journals are documented as evidence, not automatic resume. These are useful operational guarantees with stated failure limits.

## Findings and required repairs

### Major 1 — Make the diagnostic decision boundary the paper's central result

**Classification: evidence/expression gap; not a demonstrated functional implementation failure.** The public service reproduces a structural Softmax clue and a qualitative fusion decision. Its measured intervals cannot generally be interpreted as uninstrumented local costs. `paper/sections/06-evaluation.tex` and `integration/evidence/ascend-wait-fidelity-20261015/` retain the decisive adverse observation: original waits differ by 76.8%/83.4% between all-site and wait-only modes even though whole-task perturbation can be low. The BK intervention's direction survives; the subsequent output-tile wait direction does not. The minimal two-read control has zero-tick spans with advancing counters and does not bound fusion wait error.

The manuscript already acknowledges this; I am not asking it to retract a nonexistent accuracy claim. The remaining weakness is organization: the study's richer, conditional shared-clock research visualization comes before the reusable service's much narrower output, so a reader can still overestimate what the system itself recovers. The first-page summary of 5.31× recovery also needs the same distinction that appears later.

**Finite repair:** give a compact evidence-to-decision table in the main paper: public observation, permissible inference, proposed intervention, independent validation, and unavailable quantity. Put the mode-sensitive wait result next to the fusion diagnosis. State immediately that the current service replays the first diagnostic direction retrospectively and that the second step rests on cardinality/loading structure and independent task timing. Validate the table against the existing 120 waits, original CFG/signal counts and retained performance captures; no new hardware or cross-device tool port is required. If the authors instead want accurate unperturbed waits, dynamic-generation pairing or a cross-actor critical path, those require new measurement mechanisms/independent reference evidence and cannot be repaired by text or a hash audit.

### Major 2 — State a usable request envelope, including compilation feasibility

**Classification: implementation limitation plus presentation gap, not invented completeness.** GCU default scalar all-site GELU reaches a 900-second compile timeout; the vector 36-case matrix takes 70.85 minutes and retains 4,599 events while dropping 21,996. Selected-store scalar collection has about 3% device perturbation but about 5.2 ms host latency. Ascend small RMSNorm remains intrusive even after semantic selection; long-K collection costs 12 ms host calls and hundreds of MB per small session. These facts are directly retained in `paper/sections/06-evaluation.tex` and the corresponding backend evidence. A working selected offline request is useful; a common vocabulary must not imply practical arbitrary all-site profiling.

**Finite repair:** make a main-paper capability/cost table name default versus explicit alternative, annotation/selection prerequisites, tested compilation envelope, loss semantics, device/host/export costs and rejection conditions. Document a concrete bounded first request for each backend and the known GCU all-site compile failure. Retain the negative experiment. Existing functional evidence supports the narrower service; faster general all-site compilation would be a separate implementation project, not a prerequisite for the stated selective offline scope.

### Major 3 — Convert integration experience into inspectable systems knowledge

**Classification: expression/significance gap with a conditional structural risk.** The best contribution is not a new IR, multi-vendor interface, compiler insertion or selectable ring buffer. [KPerfIR](https://www.usenix.org/system/files/osdi25-guan.pdf), particularly its introduction and compiler/tool design, already supplies compiler-centric fine scopes, loop/asynchronous analysis and NVIDIA/AMD portability. The [Proton author conference abstract](https://2026.cgo.org/details/cgo-2026-papers/23/Proton-Towards-Multi-level-Adaptive-Profiling-for-Triton) supports region selection, custom metrics, multiple abstraction levels and vendor/instrumentation unification. Its unavailable full text does not establish missing features. Cached primary PASTA §III-G explicitly covers semantic/timing normalization and vendor handlers. The candidate properly credits these foundations in §8.

**Finite repair:** elevate the three failure→invariant→negative test→validated consequence chains already in §7 into the contribution argument, and explicitly identify inherited compiler/Debugger/collector mechanisms. Add small concrete output excerpts for the missing-word publication counterexample and dispatch/compute double-counting boundary. Existing retained evidence can substantiate these lessons. Do not infer superiority over unrun tools. If, after that framing, the claimed contribution remains merely three adapters and contracts, the deficit is structural: more green tests or additional vendors will not establish significance. The minimally needed condition would be a consequential new diagnostic/operational insight beyond integration breadth. This candidate already has plausible examples; acceptance still depends on how significant reviewers find them.

## Unsupported interpretations and stopping condition

The evidence does not support universal source-operation attribution, exclusive cost ownership from locations, dynamic flag/buffer/iteration identity, engine occupancy from source brackets, arbitrary pipelined NVIDIA scopes, certified NVIDIA/GCU nanosecond conversion, cross-actor/native shared origins, representative local timing from low whole-task overhead, low end-to-end collection cost, production adoption, or final-source performance numbers obtained by relabeling historical captures. Most are already correctly excluded. NVIDIA clean performance was deferred; functional NVIDIA correctness still matters and has retained evidence, but its CPU regression does not certify timing behavior.

A finite technical/text/evidence iteration can produce a credible submission under the actual selective offline scope: reconcile version labels, bring the existing adverse measurements and decision chain into the main argument, specify the usable request envelope, and complete drafting. No unavailable production deployment, new accelerator port, full Proton paper, or shared-clock mechanism is necessary for that scope. Broader timing/causal claims would require genuinely new evidence or mechanisms, and OSDI acceptance cannot be made a finite engineering guarantee.
