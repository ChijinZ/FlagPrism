## 确认问题处置

R3-M1：新增验收段可能被理解为每后端无条件支持双 stream，与既有 E03/goal 的预登记支持边界不够一致。root 确认存在措辞歧义，选择沿用原合同：资格冻结前逐后端记录 two-stream/host-thread/graph 支持表；已支持两 stream 的路径必须真实测试，不支持的组合必须在产生本次设备副作用前拒绝并验证恢复。不允许失败后缩小资格，也不能以拒绝项声称保留了跨 stream 行为。设计 §8.7 与验收 §8.3 同步修订，执行合同保持原字节。

三席复核均确认与原合同一致、无新增矛盾，R3 明确关闭 M1。没有未处理的确认设计缺陷。

## 判断与剩余风险

**设计合理，可以按 P01 继续工程实施；完整三后端可交付性尚未实证。** 三席共同指出以下工作不能由设计认可代替：

1. 最终编译对象中的计时边界、纯算术顺序及优化后的 M:N 源归属。
2. timer→实际记录位宽→decoder→时间单位/误差/epoch 的完整链，尤其跨主体比较。
3. 普通算子的真实 submit/commit/部分 wait、buffer 复用与 generation 动态关联。
4. 独立 owner、发布可见性、并发/异常回收，以及真实 Trace Processor 和 Perfetto UI。

这些项已有 P01/P03/P05/P06/P07/P10、E 场景与 SQL/UI 门，保留为待设备验证，不误列为已确认硬件不可能。当前无后端完整 P01 通过；最终独立数学和三个额外代码走查仍须实施后完成。
